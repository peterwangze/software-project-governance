# 治理工作流保留什么，下一步怎么走

维护者在决定是否加规则、接工具或退出一项能力时使用这份说明。成功的尺度是用户在正常入口拿到了什么，以及下一位接手者能否从同一份事实继续。2026 年 11 月 18 日从本项目治理记录提炼。

## 哪些决定值得留下

| 治理记录中的教训 | 对当前事务的取舍 |
| --- | --- |
| AUDIT-160 复盘的 12 项候选全部来自内部信号。DEC-377 冻结了尚无新需求支持的工作。 | 提议新增职责时，指出真实用户、受阻的操作、可观察的交付差异。历史上有过这条流程，本身不足以让它继续进入每次会话。 |
| DEC-388 把原始目标、验收缺口和下一步排序连起来。DEC-389、393、395 在 DSH 验证了宿主可以保有目标、授权和直修回执。 | 工作流负责意图识别、事务分解和路径规划，把完成条件写进已有契约。由宿主提供身份、权限、预算、隔离和工具入口。一次已证实、已获授权的修复可直接动手，沿同一成品验收。 |

| DEC-150 将事实依据、变更影响、可回滚与用户数据完整性列为质量原则。旧迁移预览曾在没有运行数据时显示十章游戏内容。 | 过程看护和循环演进依赖真实观察。缺数据时保留未知，坏数据阻止写入。失败沿具体缺口换路。领域模型、素材与验收工具由领域项目或社区维护，治理只消费其证据。 |

## 一次交接是否真的有人消费

11 月 18 日的 Codex 续派最初只有目标与限制。协调者在现有描述和验收标准里补入两种 YAML 读取方式，独立 QA 再从隔离的 DSH 0.2.1-rc.2 执行 `dsh --profile headless --dump-default-config`。同一份 382 行配置中，PyYAML 6.0.3 的 `compose(..., Loader=SafeLoader)` 保留了第 7 行的 `!!js` 标签，DSH 自带的 js-yaml 4.3.2 默认 `load` 在该行报错。两次独立导出 SHA-256 一致，采用前者即可检查配置，无需执行标签内容或给治理核心添加依赖。[PyYAML 节点 API](https://pyyaml.org/wiki/PyYAMLDocumentation) · [js-yaml 上游](https://github.com/nodeca/js-yaml)

这个样本验证了候选交给下一人后确实被用于验收。离线诊断同时返回 `S5=NOT_RUN`，所以运行态插件状态仍未知。当天还通过了已有单项直修的 CLI 回归，DSH 模型层的新任务交付和两条路径的端到端耗时仍待同条件采样。

## 下一次演进从哪里开始

1. **接真实事务。** 先保留原话和正常入口的完成条件。新领域、通用实现、重复失败或资源选型触发当前宿主的探测。由能够看到问题的人做最小试验，使用现有派发或直接执行路径传递结果。[探索协议](../../skills/software-project-governance/references/behavior-protocol.md#m10-主动生态探索协议exp-0105) · [派发模板](../../skills/software-project-governance/references/agent-dispatch-template.md)
2. **以成品决定是否扩大。** 在 Codex 和 DSH 分别记录首次有效操作、采用或淘汰的资源、受限原因以及实际交付物通过了什么验收。比较同一输入、权限、预算下的旧路径与候选路径。未触达验收的样本计入分母，保留未知。只有重复观察到同一交接缺口，才考虑把解决办法提到通用层。
3. **持续退出旧责任。** 对下一项候选找实际调用者、独有保护及其归属。以旧 tag 回放历史发布，用当前正常入口和反例检验仍生效的承诺。过期检查、模板和伴随的自测应一起退出。现行发布签收、未完成的事项和仍在使用的证明保留到承接点可以验证。

旧版的审查、发布说明和一次性诊断可从清理前的 Git 树按原路径读回，例如 `git show 7b9fd37:docs/research/audit-160-evolution-thesis-2026-10-28.md`。宿主私有运行记录由宿主保管。[清理前的版本树](https://github.com/peterwangze/software-project-governance/tree/7b9fd3720376549c53b06d4fc362f5fb0c96e40b)
