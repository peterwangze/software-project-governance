## 4. 根因模型（Coordinator 草案 × arch 顾问联合裁定）

**Coordinator 草案**：「治理双轨分叉」——冷面（Gate/主表/TPA/风险/锁/执行包）手写维护、热面（滚动窗口+证据+审查+对话）执行驱动，长程压力下注意力回归「把活干完」，冷面第一个被牺牲，且无机制因冷面过时而 FAIL，分叉不可自愈。反证考量：前半夜高密度记账证明冷面在低负载时可维护——支持「压力+无执法→衰减」而非「根本不可维护」。

**arch 裁定**（采纳）：双轨分叉**成立但只是失效形态**。更底层：**治理状态不是执行权限的权威来源；身份、版本、义务没有绑定到不可绕过的动作边界**。三个深层缺陷：
1. **没有唯一事实源与稳定身份**——任务 ID 可换语义、计划与执行各自增长、报告与机录各自声明结论，冲突时无「谁有权决定事实」的规则；
2. **验证未绑定不可变对象**——REV-009 的本质不是「没提交」，而是审查结论没有绑定可重现的代码/依赖/环境/验收标准版本；
3. **优化对象替代**——系统优化了代码量/测试数/审查活动，却从未持续证明「用户能完成一条游戏体验链」。

根因排序（arch，因果层级重排）：**①无执法闭环（最直接）→ ②手写维护成本（同一事实多处表示，规模上升必然漏记冲突）→ ③goal 机制不匹配（blocked 后仍运行=「能否继续」无唯一裁决者）→ ④上下文断裂（放大器而非首因——过度投资提示词工程而保留控制缺口是错误方向）**。

对 Coordinator 草案反证的裁定：早期记账正常只证明低负载可维护，不证明长程可维护——维护成本随任务数×并发×审查轮数可能超线性增长。
