## 总裁决

我认可第一轮的总体方向，但建议修正三个关键点：

1. **先封住手写入口，再逐表迁移存储；不要把"全部 JSON 化"设为写入器上线的前置条件。**
2. **闭环采用前向恢复，不做跨本地文件、Git commit、远端 push 的整体回滚；任务完成、闭环完成、发布完成必须分开。**
3. **过期基线不能继续给出确定性判决，但也不能一律降级后放行。应区分"规则评估失效"和"是否允许继续"。**

现有证据足以支持"优先补写入器和编排器"，但不能推出"CLI 天然可靠"或"存储格式转换本身能消除事故"。主要收益来自：**约束入口、版本化写入、可靠恢复、减少确定性步骤中的 LLM 往返**。

### 一、目标与假设

目标定义：LLM 负责提出判断和意图；软件负责合法落盘、推进流程、执行门禁、报告恢复点。任何失败都不要求 LLM 手工修复治理文件。

三个假设：治理数据主要位于本地 Git 工作区无常驻数据库；多 agent 可能操作同一工作区/不同 worktree；允许改变内部存储但必须保留可直接阅读、可 Git diff 评审的 Markdown。

发布前需确认三项事实：支持的操作系统/文件系统、并发部署形态、任务"完成"是否要求 push 成功。

### 1. 状态机所有权与并发

**「受治理状态的唯一受支持写入入口=CLI」升硬边界。并发采用 CAS 与短时写入锁组合，不是二选一。**

三职责分离表：状态机判断转移合法性（不判成果正确性）；CAS `expected_revision` 拒绝过期更新（不单独保障写互斥）；短时存储写入锁保护 READ→比较→WRITE 临界区（不覆盖分钟级推理/push）。agent-locks 是业务锁不能代替存储写入锁。

写入流程五步：LLM 提交（task ID/期望版本/目标状态/证据引用）→ CLI 取短时锁 → 重读校验（CAS/锁所有权/合法性）→ 计算新状态原子替换 → 释放返回新版本+结果码。

关键风险：所有任务共用一个 JSON 文件时任务级 revision 不够——共享文件需受锁保护的重新读取合并更新或聚合版本。CAS 冲突不自动换版本执行——返回当前状态与冲突原因由调用方重判；相同 operation_id 重试返回原结果。

边界：本地锁不协调不同 clone/worktree（跨副本冲突由 Git 集成处理）；「CLI 唯一写者」是接口契约非权限隔离——直接编辑仍可能，靠一致性检查拒绝；紧急修复走受审计的 repair/import 命令。

### 2. closure-chain 失败语义

**默认断点续传、幂等重入；不支持整体自动回滚。**（push 成功但本地误判失败的回滚可能破坏别人已读状态；跨副作用无可承诺原子事务。）

持久化清单：closure_id/输入摘要/绑定任务版本/已完成步骤及产物 ID/当前步骤失败原因重试条件/预期 commit SHA 目标远端分支/外部动作结果不明标 UNKNOWN。

恢复规则表：evidence 已写 tracker 未更新→复用原 evidence ID 从 tracker 续；commit 成功状态未落盘→核验目标 commit 不重复提交；push 凭据失效→保留本地 commit 等凭据修复续；push 超时结果不明→先查远端是否含目标 SHA 再决定；分支被推进→显式报告冲突不自动 force/rebase。

不要把 5-8 步顺序直接固化——先定义依赖：任务业务完成/关闭锁/形成 commit/远端同步是不同事实。push 失败不应让任务回到"进行中"。**不能要求"push 成功的状态记录"被包含在它描述的那个 commit 里（无限追加自指）**——闭环运行状态与业务记录分离。

事件载体：复用既有 loop 事件协议/持久化/恢复模式；不默认塞同一日志文件（类型/schema 版本/closure_id/顺序号；不兼容则独立 closure 日志——不增加新机制）。状态库常规读取；日志作审计+幂等核验+故障恢复（"不作日常读取路径"≠"恢复也禁止读取"）。

过渡期：未接管流程=人工逐条调用原子 CLI（仍禁手改）；已接管=closure-chain 唯一推进者；故障降级=显式暂停/接管后原子 CLI+编排器核验恢复。**不允许人工协议和编排器同时推进同一 closure。**不反对 `closure run/resume` 门面命令——命令数量不是复杂度指标，隐藏状态和失败不可恢复才是。

### 3. evidence-append schema 边界

**骨架必检 + 类型化引用可解析性检查 + 语义判断不自动裁决。**文件存在性不是越界；用存在性证明证据充分或把所有引用当本地路径才是越界。

引用类型表：仓库文件（指定工作区/commit 中存在+路径合法）/Git 对象（commit/blob 可解析）/治理记录 ID（存在且类型正确）/外部 URL（语法合法；默认不联网验证）/人工观察（内容非空+判断来源明确+不假装已验证）。证据尽量锚定 commit/blob 或内容摘要（仅"当前路径存在"会随文件演化失效）。

区分 reference_validation（可解析/不可解析/暂不可验证）与 verdict（证据是否足以支持判断——人或 LLM）。禁止 CLI 从"文件存在"推导"测试通过"；不通过关键词/最小字数/白名单拦"空话"。

存量 ×415：标记 legacy 批次只检读取安全+必要结构；新增执行新规则；存量被改写或支撑新高风险结论时再要求补锚；不做一次性全量语义整改。

### 4. 门禁参数数据化

**数值门强制携带 provenance；拒绝统一"过期即 ADVISORY 并放行"。**至少记录：测量时间/测量器版本/来源命令/测量对象 commit 或内容摘要/范围分子分母排除规则/阈值依据/有效期失效条件。新鲜但口径不同的数字同样不能比较。

分离：评估结果 PASS/FAIL/NOT_EVALUABLE；继续策略 BLOCK/ADVISORY。过期/范围变化/测量器不兼容→NOT_EVALUABLE：研发趋势与试点效果门通常 ADVISORY+触发重测；发布/安全/数据完整性门通常 BLOCK 等重测或明确授权豁免。自动重测失败不默认通过；豁免有范围/理由/授权/失效条件。

"85% 数学不可达"类确定性矛盾应检查冻结分母/排除集合/指标口径——能确定性发现的矛盾返回**门禁配置错误**而非用户工作失败，不自动调阈值。

### 5. 机录 CLI 自身可靠性

**写后自检、守护测试、灰度开关必须交付，但三名称不足为验收标准。**八条：写前完整验证（先算候选结果再校验 schema+跨记录约束）/幂等与冲突协议（同操作重试不重复追加；同 ID 不同输入拒绝）/可靠落盘（显式 UTF-8/同文件系统临时文件/原子替换/声明平台）/写后重读（重新解析查目标修改与未改数据不变）/dry-run 与结构化结果（预览 diff；区分校验失败/冲突/可重试/需介入）/恢复路径（不留只能手改的半成品）/守护测试（键碰撞/中文 GBK/缺行/重复执行/并发覆盖/崩溃点/Markdown 特殊字符/legacy 数据）/渐进启用（按记录类型接管；关闭新编排退回原子 CLI 不退回手工写入）。

多文件不因各自原子替换就宣称事务原子：JSON 成功投影失败→显式"源已提交投影待修复"态，禁后续 commit，重入只重建投影。写后自检异常不无条件恢复旧文件（可能覆盖后来合法写入）——恢复受版本检查保护。

### 6. 统一迁移序列

**按能力纵向切片的 strangler，非"全量存储分离完毕才做编排"。**阶段改名避免混淆（M0 契约冻结：状态语义/版本协议/操作 ID/错误码/兼容边界——fixture+契约测试；M1 原子状态件 B-1/B-3；M2 追加写入器 B-5/B-2；M3 闭环纵切一条高频标准链含 commit/push 失败恢复；M4 逐表源迁移；M5 扩展与收缩）。M4 可与 M1/M2 合并到某张表不要求全局后置；核心是**每张表只有一个规范源不能双主写入**。

**0.86.0 范围**：M0+M1+M2+M3 一条标准闭环（必须覆盖 commit/push 失败恢复）+必要存储迁移+接管范围内零手写硬门禁+archguard 纪律。tracker 表格格式难以安全写回则 JSON 化并入 M1；不为其他未用表的全量迁移延迟 B-1。**0.87.0+**：closure 取消/重开/异常接管分支、JSON 源扩面、B-6/B-7、单体持续缩减。

**对第一轮的明确不同意**：不同意"全量 P1 存储分离→P2 编排"严格串行；不同意狗粮自举放最后（**每个里程碑立即狗粮**）；单体收缩是每批实施约束不单列版本。

### 7. 其余独立判断

六层架构同意作为目标但不要求每命令贯穿六层（复用组合根，不为小写入器造框架）。JSON 源+Markdown 投影同意终态反对一次性铺开——**评审可读性写入投影契约**：行序稳定不因改一行全表重排/换行转义列格式确定/不注入每次变化的生成时间/单条更新局部 diff/可从源恢复/JSON 同样稳定便于 diff。区分治理事实（结构化源负责）与人写设计说明（保留 Markdown 或只投影标记区域）——不为统一存储把说明文档降格为 JSON 字符串。drift 阻断 commit/发布但提供可直接执行的修复命令；迁移恒等验证字段/引用/状态/ID 语义+plan-hash 契约，不假定字节恒等。

状态库+审计日志同意；拒绝日常全量重放也拒绝"日志绝不读取"字面约束。区分业务当前状态/closure 执行检查点/审计事件——前两者是结构化状态，不能为"日志只审计"让恢复上下文消失；三者一致性沿用 ADR-014 协议。

判断外壳同意但枚举 verdict 不等于机械执行全部后果——撤销已推送结果/破坏性修复仍需明确授权。"六模式封顶"限制新增基础设施与一致性机制，不允许被误解为不许增加必要的状态/结果码/测试。

### 规划缺失关键点

① Git 副作用边界：closure 不默认 `git add -A`（限定产物路径+commit 前检查暂存区并发变化）；push 目标来自受控配置；不接受证据文本拼 shell 命令；不记录凭据；默认禁 force-push。② 模型输出始终不可信输入：ID/路径/引用/命令参数类型边界检查；投影转义管道符换行；外部 URL 默认不自动抓取（防追加记录变隐式网络入口）。③ 兼容与回退不是一个开关：schema 版本/旧 CLI 遇新 schema 拒写/迁移前后回退条件——**新格式产生新数据后不能靠恢复备份回退丢数据**。④ 完工指标量化：每票确定性环节 LLM 往返数/闭环耗时分项（等待判断/等待外部）/首次写入成功率/冲突重试投影漂移人工恢复次数/被接管流程手写次数/故障恢复零重复零丢失。文件规模不足以证明存储瓶颈——先减少回合与重复解析，不引入数据库。

### 最终建议

**0.86.0 交付"四类可靠原子写入器 + 一条可恢复标准闭环 + 接管范围内零手写"，而非"全面 JSON 化+全流程自动化"。**发布前用一条真实任务演练：在每个持久化和 Git 边界中断并恢复，证明不丢记录、不重复追加、不误提交旁路文件、不因 push 失败回滚业务事实。
