# v0.100.0 回滚方案

当会话启动失败、交付记录无法重读、既有项目升级后不能执行验收，或远端标签与签核的转换提交不一致时，先保存触发命令、原始输出、版本和提交 ID。

## 消费项目恢复

1. 暂停会写入该项目状态的工作。分别备份项目治理数据、宿主配置和当前安装元数据，核对备份能读取。保留升级后生成的工作单元、反馈证据及工件。
2. 在独立目录用 `git worktree add --detach ../spg-rollback-099 v0.99.0` 取得前版；已使用插件管理器的宿主可通过其版本固定机制选择同一标签。在项目副本中按旧版本的宿主指引加载，运行 `governance-bootstrap --format json` 并重放一项升级前通过的真实操作。
3. 旧版本对 v0.100.0 新学习记录的解释和继续写入未经跨版本保证。用升级前的同版数据备份进行恢复演练；发布后新产生的证据另存，在已经验证的新版上复读核对。恢复前核对项目和安装目录的实际路径。
4. 验证副本通过后再切换安装，重启宿主并复测同一操作。仅当实际启用了宿主专项迁移时，使用该次升级生成并核对过的备份还原对应配置。

## 仓库与已发布版本

DSH 目录模式升级时，先备份现有的 `.agent-presets/governance` 完整目录。遇到旧版本缺少来源记录、内容被手工编辑或宿主基础预设无法读取时，保留原件。在独立的 `DSH_HOME` 安装新预设并运行 doctor S1、S2，对照差异后再切换。回退到 `v0.99.0` 时须使用与该预设匹配的宿主，桌面版本 0.2.2-rc.5 已删除旧模板引用的 `./list-agents`。

- 打标签前发现阻断时，保留失败候选和日志，修正问题后重新获得候选 CI 和审查结论。
- 公开发布后保留既有 tag 及其指向，在 GitHub Release 说明中记录影响及恢复方法。需要纠正产品时在 master 提交正向修复或定点 revert，为修订版重新签核和打标签。
- 核对 `git ls-remote origin refs/tags/v0.99.0 'refs/tags/v0.99.0^{}' refs/tags/v0.100.0 'refs/tags/v0.100.0^{}'`，将剥离后的 commit 与相应清单逐一对照。[发布清单](release-checklist-0.100.0.md)
