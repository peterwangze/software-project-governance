## 5. D 面（跨 profile 重复）专项测算

- **行级重叠**：standard 278 非空行中仅 **1 行** strict 没有（FIX-278 编码防护，§8.1）；strict 297 非空行中 **16 行** standard 没有（15 行 Strict 规则节 + 1 行归档完整性强制）。共享 213 个唯一行。
- **共享面 token**：两块各自由共享行组成的人脸均 = **7,016 tok / 23,449 B**（同值——standard ⊂ strict，strict = standard + 306 tok）。
- **去重收益定性（关键论证）**：
  - **维护面收益 = 7,016 tok 双份维护消除**——单侧维护 + 投影复用后，瘦一份 = 两 profile 同时受益（努力乘数真实存在）。
  - **resident 收益 = 0**——每会话只注入 profile 选定的**一个**模板块（profile-selected surface，`injection_budget.py` L98-118），standard/strict 从不同时注入；跨块去重不减少任何单会话的注入量。
  - **双计数警示**：任务公式"A + D 去重 + C×r"中若把 7,016 计入 resident 余量 = 把同一文本算两次（乐观倾斜）。**本报告判定只用 resident-effective 口径**（A + C×r），D 面单列为工程收益与约束侧事实。

## 6. 余量测算 vs 需求

实现率取值论证：
- **A@100%（乐观）**：A 面全部引用化——**不可达**。模板自身契约标注 pre-skill-load 自包含（§3.1 #10 原文），且 Step 1 六段 fallback 恰在聚合命令不可用时才被需要——降级路径的行内摘要必须保留。
- **A@70%（现实）**：触发器一行 + 降级摘要行内保留；升级序列 A-E、a-j 清单、路由表、三类决策清单等明细外移 SKILL.md 按需加载。
- **A@50%（保守）**：契约不变（维持自包含）时只做无损紧缩（合并重复表述/删修辞强调）。
- **C@10%**：C 节为稠密祈使规则（模式契约 983、守卫 178、strict 规则 291），token 是唯一领域词（模式名/MUST 条款/量化数字），20% 无损不可信；10% = 措辞紧缩上限。B = 0%。

| 情景（resident-effective） | standard 余量 | vs 需求 4,718 | strict 余量 | vs 需求 4,918 |
|---|---|---|---|---|
| 乐观 A@100% + C@10% | 5,697 | **+979**（1.21×） | 5,726 | **+808**（1.16×） |
| 现实 A@70% + C@10% | 4,023 | **−695** | 4,052 | **−866** |
| 保守 A@50% + C@10% | 2,907 | −1,811 | 2,936 | −1,982 |
| **break-even A 实现率**（C@10%） | **82.5%** | — | **85.5%** | — |
| A@85% + C@10% | 4,860 | +142 | 4,889 | **−29（不达标）** |
| A@90% + C@10% | 5,139 | +421（8.9%） | 5,168 | +250（5.1%） |

含 D 的机械求和（A 5,581 + D 7,016 + C@10% 116 = 12,713）远超需求，但如 §5 所述属 resident 双计数，**不作为判定依据**。

## 7. 判定建议（呈 Coordinator→用户；非最终裁决）

### 建议：**条件 go**

- **依据**：resident-effective 余量在乐观档覆盖需求但安全边际不可靠（100% 实现率不可达，§6）；现实档差 −695/−866。**可达性完全取决于一个架构契约决策**——模板块从「自包含（明细全部 resident）」改为「触发器行内 + 明细按需（SKILL.md progressive load）」。该决策一旦作出，A 面 69.4% 集中在 3 节（step1/question-rules/step05），处置面收敛、工程上可执行。
- **条件 1（处置特定节）**：以 step1（2,761）、question-rules（614）、step05 路由（498）为主对象做「触发器 + 按需明细」改造，**按 A@90% 规划**（5,139/5,168，边际 +421/+250）——按 85% 规划 strict 差 29 tok 不达标（break-even 85.5%）。
- **条件 2（D 面纪律）**：瘦身穿共享基座一次性实施（standard ⊂ strict，一份工作双 profile 受益）；**禁止**把 D 去重计入 resident 收益向用户呈报。
- **条件 3（strict 为约束侧）**：strict 恒需多削 200 tok（4,918 vs 4,718）且 C 面多 291 tok（Strict 规则本体不可引用化）——达标判定以 strict 为准。
- **fallback（如契约变更被否）**：维持自包含、只做无损紧缩 → 余量 ≈ 保守档 2,907/2,936 ≪ 需求 → **no-go（R1 触发）**，呈用户三选一（DEC-217 保留边界——Coordinator 呈报）。
- **附带杠杆（范围外，供三选一准备）**：若 persona（1,673）或 agent-instructions（~1,923）纳入瘦身/引用化，entry 侧需求线放宽——属范围变更决策，须用户裁定，不改变本报告判定逻辑。
