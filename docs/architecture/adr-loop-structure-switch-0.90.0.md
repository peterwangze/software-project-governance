## 1. 背景

DEC-097（2026-07-10）决议「重构式——loop 为唯一模型，G1-G11 退化为 loop-setup」。双报告根因分析（AUDIT-155 行为面 8 根因 / AUDIT-156 结构面 10 冲突点，R1 通过）证实：该决议在 0.65~0.89 的 32 个发布版本中停留在能力交付层——**生命周期语义的权威链从未切换**，数据（plan-tracker 单一 Gate 表）、判定（auto_judge_gate 走 classic 执行注册表）、协议（入口层零 loop 语义）、呈现（bootstrap next_gate/stage 线性坐标）四层闭环仍共同维护 classic 模型，持续把 agent 行为拉回「往下一个 Gate 推进」。arch 顾问对齐确认核心诊断，并修正根因表述、补齐目标驱动控制面与假切换风险警告。用户经 DEC-252 裁决：**候选 B 结构切换终态授权（arch 推荐形态），本 ADR 为五步路径第 1 步**——先定义语义与权威，不先翻 registry。

## 2. 决策

采用候选 B（结构切换）为目标架构终态，受以下九条约束定义：

### 2.1 语义与权威链——五概念关系

| 概念 | 语义 | 权威链位置 |
|---|---|---|
| **项目目标** | 项目为何存在、成功标准是什么；一切工作的最终裁判 | 目标层权威 = plan-tracker 成功标准 + execution packet `product_success_contract`；不派生于任何 Gate/loop 状态 |
| **flow unit** | 目标之下可独立推进/验证/交付的工作单元（skill/module/release-candidate/…） | unit 注册与 lane 状态权威 = `flow-unit-runtime.json`（宿主级）；由迁移/派生工具维护 |
| **loop** | unit 的工作组织方式（尝试/反馈/学习/重新规划的迭代容器，三层嵌套 setup/inner/middle/outer） | loop 拓扑权威 = `loop-engineering-registry.json` loop_gate_semantics + fuses；loop 运行态（第几轮/fuse 是否熔断）权威 = flow-unit-runtime 的 loop_state |
| **Gate** | **作用于具体动作的看护门禁**——某类动作（发布/合并/迁移/翻转）必须满足什么条件才被授权；不是阶段成就，不是项目状态坐标 | Gate 契约权威 = 本 ADR §2.5 + 按 loop 角色标注的检查策略（见 §2.3 三分离）；**Gate 状态不是项目状态** |
| **版本** | 持续演进的发布切面（见 §2.9 语义界定） | 版本事实权威 = CHANGELOG + tag/ledger 发布链；与 Gate/loop 无派生关系 |

推论：项目状态 = Σ(unit lane/loop 态) + 目标差距，**不存在**单一全局阶段坐标；「下一个 Gate」不是合法状态查询。

### 2.2 事实源、派生视图与允许写入方

- **事实源**：① 目标层 = plan-tracker 成功标准节 + execution packet 契约字段；② unit/loop 运行态 = `.governance/flow-unit-runtime.json`；③ loop 拓扑/熔断上限/暂停点 = loop-engineering-registry.json；④ 证据 = evidence-log（机录优先，按 C-10 修复强化校验）。
- **派生视图**：plan-tracker `## Gate 状态跟踪` 表（切换期）= 由 unit lane 状态**单向生成**的兼容投影——不可人工直改、不参与动作资格判定（arch 对 C 的纠正同样约束 B 的兼容面：只读投影 ≠ 第二权威）。
- **允许写入方（按事实源逐一列明——R0 修正 2026-09-26）**：
  - 目标层（plan-tracker 成功标准节 + packet 契约字段）：**用户/Coordinator 经既有协议合法写入**（目标可变更是 §2.7「何时调整或停止」职责的前提——目标层不是机器维护面）；
  - 证据层（evidence-log）：机录路径优先（review-record/governance-store 等既有写入器），Coordinator 直写沿既有 M1.2 快速通道规则不因本 ADR 变更；
  - unit/loop 运行态（flow-unit-runtime）：仅限迁移工具（loop-migrate）与 loop 事件处理器（process_gate_result 链）；
  - 兼容投影（切换期 Gate 表）：仅限派生生成器（由 lane 状态单向生成）。
  - **Check 拦截的精确范围（R0 修正——原「手工直改任一事实源」字面过宽）**：漂移校验仅约束**机器维护面**（运行态 + 兼容投影）——绕过该层合法写入方的直改 → Check 拦截；目标层与证据层的合法人工/协议写入不在拦截范围（漂移校验为切换前置项，见 §6 步骤 2）。

### 2.3 三权威分离（拓扑 / 检查策略 / 运行状态）

`loop_gate_semantics` 描述**拓扑**（哪个 Gate 在哪个循环扮演什么角色、失败回哪个 loop）——它**不**自动承载：① 证据要求（每类动作查什么证据、证据多旧算失效）；② 授权策略（哪些动作需用户确认）；③ 执行安全策略（哪些检查 fail-closed）。三者分别由：检查策略（按动作类型定义，§2.5）、授权策略（既有 interruption policy/M5.3 关键决策边界，原样继承不降级）、运行状态权威（flow-unit-runtime）承载。**迁移实现 MUST NOT 把三者折叠进 registry 单文件**——那是下一种 God Object。

### 2.4 单一判定权威约束（DEC-252 裁决③）

**每宿主、每类授权动作，任一时刻只有一个有效判定权威；新旧实现短期共存于代码库，但任一时刻只有一个产生真实副作用（判定/写事件/改状态）。** 过渡期实现要求：
- 每个判定产出 MUST 携带权威署名（`authority: classic-g1g11 | loop-engineering`），判定与事件可追溯来源；
- 分族授权票翻转 = 把某族动作的权威署名从 classic 切到 loop-engineering 的唯一合法方式；翻转前 loop 侧输出仅 WARN/影子模式，不产生副作用；
- **禁止假切换**：若某动作的判定数据实际仍由 classic 派生或来自未经验证的数据源，则该动作的权威仍是 classic——词汇替换/registry 翻转本身不构成切换（arch 第 4 判断成文化）。

### 2.5 Gate 契约（适用范围 / 证据有效期 / 失败后允许动作）

- **适用范围**：Gate 按动作类型定义（发布、合并、迁移、授权票翻转、外部副作用），按所属 unit 生效——同族动作对不同 unit 的检查集可不同（loop-engineering-registry 的 per-unit gate_references 词汇沿用）；**不存在「项目的当前 Gate」**。
- **证据有效期**：证据绑定 (unit, 产物版本, 检查策略版本, 审查主体) 四元组；unit 产物变更、策略版本升级或审查主体变更使既有认证失效；仅显式声明可复用的证据（如未变更依赖的扫描结果）可跨轮复用——复用规则在检查策略中逐条声明，不默认有效。
- **失败后允许动作**：**「门禁失败可以阻止某个动作，但不应把整个项目定义为『停在某个阶段』；其他独立、安全的工作仍可继续」**（arch 契约语句，本 ADR 采纳为规范语义；可追溯性注记——R0 修正 2026-09-26 D-4：该逐字语句为 arch 会话意见，磁盘存档 `audit-155-arch-advisory-0.89.0.md` 为摘要版〔其 L74 自述完整原文随会话记录〕，语义与存档 §七 Gate 层职责一致）。即：Gate 失败阻止的是该 unit 的该类动作（如发布），不冻结其他 unit、不冻结该 unit 的其他动作类型、不产生「阶段失败」状态；失败 unit 的正规出路是所属 loop 内迭代（on_fail=iterate-enclosing-loop）或按 fuse 升级，而非「回退阶段」。

### 2.6 unit 锚定——fail-closed

**错误锚定比缺失锚定更危险。** 自动推断（task→unit 映射）仅限唯一可解释匹配（单候选且名称/依赖链可解释）；歧义（多候选）或缺失时：不猜测、不静默创建、要求 Coordinator/用户确认后落盘映射。unit 缺失不是错误状态——未注册工作按「无 unit 上下文的动作」处理，受通用护栏约束，不享受 unit 级认证复用。运行时数据缺失或 unit 歧义时，**不自动退回 classic 继续执行敏感动作**（发布/外部副作用/授权翻转）——敏感动作改为等待确认（arch 五步④成文化）。

### 2.7 目标驱动控制面（三层职责分离 + execution packet 接通）

**三层职责**（arch 第四路径——这是 B 的内部职责划分，不是第四套并存模型）：

| 层 | 职责 | 载体 |
|---|---|---|
| **目标层** | 为什么做 / 优先做什么 / 何时调整或停止 | plan-tracker 成功标准 + execution packet `product_success_contract`（goal/non_goals/success_metrics/done_definition） |
| **loop 层** | 如何组织尝试 / 反馈 / 学习 / 重新规划 | flow unit + loop tier/round/fuse（§2.1 语义） |
| **Gate 层** | 什么动作必须满足什么条件 | §2.5 Gate 契约（作用于动作，作用于约束位置） |

**接通点（不新建引擎）**：目标驱动层直接消费既有 execution packet 契约字段（`verify_workflow.py build_execution_packet` 已定义 goal / product_success_contract / allowed_change_scope / required_evidence / done_definition / quality_budget）——切换工作是把它们从「任务级约束附件」提升为「目标层权威输入」，而非新建目标引擎。

**bootstrap 主层级**（呈现层重排——目标在前、Gate 在约束位置）：当前有效目标及版本 → 目标差距/风险/不确定性 → 推荐行动及预期贡献 → unit 与 loop 上下文 → 适用护栏/授权/证据缺口。

**激励条款（规范要求，非建议）**：「暂不新增动作」「终止低价值 unit」「等待必要证据」是**正当推荐输出**——推荐系统的价值函数以目标贡献为准，不以可见合规活动量为准；高效率 ≠ 永远制造下一项工作（arch 补充 2 成文化）。

### 2.8 classic 兼容边界与退役条件

- **角色（两相定义——R0 修正 2026-09-26，消除与 §2.4/§6 步骤 4 的相位矛盾）**：
  - **窗口内**（分族翻转窗口期）：classic 仅在**显式授权票声明的未切换族**上按既有授权继续判定——该族的在任权威仍是 classic（§2.4「任一时刻只有一个有效判定权威」即指此态），判定产出带 `authority: classic-g1g11` 署名；**已翻转族上 classic 不得残留任何可执行判定路径**（残留即在已切换域产生第二权威 = 假切换）。窗口合法性以退役三要素（本节第三条）在案为前提。
  - **窗口关闭后**（三要素满足、退役生效）：classic 降为**只读解释器 + 迁移适配器**（解释旧 plan-tracker、供迁移工具消费）——**不是可执行模型**：不产生判定副作用、不授权动作、不被 bootstrap 消费为状态坐标。**此后若 classic 在任何动作路径上仍可执行判定，则「唯一模型」未成立（假切换，§2.4）**——本句为「假切换」的定义处，供授权票与 Check 引用。
- **兼容面只读**：切换期 plan-tracker Gate 表由 lane 状态单向派生（§2.2），用户可见但无权威。
- **限期退役（不靠「以后再翻转」）**：迁移窗口三要素成文——① 负责人（每族切换的授权票 Coordinator）；② 退出条件（该族全部宿主完成授权翻转 + 行为验收通过 + 兼容消费点清零）；③ 期限（每族授权票携带，翻转票 = 退役执行器）。窗口关闭后 classic 判定路径代码进入删除候选清单（删除本身再走 change-triage）。

### 2.9 「版本永远往前推进」语义界定（成文假设）

用户理念基准「版本永远往前推进（持续演进）」在本架构中界定为：
1. **正向**：项目状态由目标差距与 unit 推进表达，不存在「停在某 Gate 等待过门」的里程碑静止态；演进是常态而非需要论证的例外。
2. **≠ 任何版本必须发布**：「暂不发布（等待必要证据/证据不足）」是正当状态（§2.7 激励条款）——不发布不构成演进停滞。
3. **≠ 护栏未满足时允许部署/不可逆动作**：Gate 契约（§2.5）阻止的是**具体动作**，不是项目状态定义；持续演进从来不授权绕过护栏。
4. 语义试金石（arch 最终验收问题原文）：「当项目目标、风险和实际状态变化时，它是否选择了更合理的工作；既不会为了过门制造工作，也不会以持续演进为由绕过必要护栏。」

## 3. 备选方案与排除理由

完整三候选比较（S-1~S-5 标准：线性偏差消除/DEC-097 继承/成本风险/可回滚/生态破坏）见结构面报告 §5.0~§5.4（引用不重复）。精炼：

- **候选 A（投影重解释）——排除**：S-2 不达标（并存=DEC-097 已否决形态）；arch 评估「可改善可见性，不解决权威冲突；先宣传 loop 而执行仍 classic 可能制造虚假能力感」。DEC-252 裁决：不作终态（如需可作限期迁移准备且需另行授权偏离）。
- **候选 C（混合渐进）——排除**：S-2 冲突（DEC-097 明确否决并存式）；arch 补充致命缺陷：原描述内部不清晰——「lane 为权威」但「判定权威不动」**分裂了状态权威与执行权威**，恰是本 ADR §2.4 单一权威约束要消灭的形态。DEC-252 裁决：落选。其合理成分（只读兼容视图、unit 桥）已被吸收进本 ADR §2.2/§2.6。
- **候选 B（结构切换）——采纳**：唯一与 DEC-097 终态一致的候选；按 arch 修正采纳增强形态（目标契约 + 证据有效期 + 行为验收 + 单一权威约束）——**裸 B（仅换状态模型）不充分**：只换 tier/round/lane 会把「为了过 Gate」变成「为了退出 loop」，故本 ADR §2.5/§2.7 为 B 的组成部分而非附加项。

## 4. 蓝军挑战（针对本 ADR 决策面）

- **ADR-RB-1 假切换：权威约束如何被机器验证而非停留在 prose？** 如果 FEAT-068 迁移完成、registry 翻转、词汇全部替换，但某读路径（如 bootstrap 聚合或某 Check）仍消费 plan-tracker Gate 表或 classic 判定产物——§2.4 被架空且无人发现（0.65.0 问题的重演路径）。缓解：判定权威署名字段（§2.4）+ 新增投影一致性 Check（凡消费 classic 判定产物的读路径清单化，翻转族变更时同步审计）+ 行为验收场景「判定来源可追溯」；分族授权票的翻转 diff 必须包含权威署名变更。
- **ADR-RB-2 目标层空壳：execution packet 契约现状是 TO_BE_DEFINED 占位符。** `build_execution_packet` 的 product_success_contract 全字段为 TO_BE_DEFINED 模板（verify_workflow.py L14308-14324 实证）——「接通既有契约」可能等于接通空契约，§2.7「目标在前」的 bootstrap 层级渲染占位符，目标驱动沦为形式。缓解：宿主激活前置条件加入「至少一个 unit 的 product_success_contract 非 TO_BE_DEFINED 且可追溯 plan-tracker 成功标准」；packet 模板占位符从可容忍升级为目标层完整性检查项（缺失 → WARN，敏感动作 → 阻断）；纵向切片（步骤 3）验收含契约非空断言。
- **ADR-RB-3 限期退役若无强制执行器，将重演 32 版本滞留。** DEC-097 交付后 0.65~0.89 未落地的教训：兼容态无期限、无负责人、无退出条件时，「兼容」即「永久」。挑战：迁移窗口到期仍有宿主未切换时，谁阻止 classic 判定路径继续被消费？缓解：§2.8 三要素（负责人/退出条件/期限）逐族写入授权票；退役条件中「兼容消费点清零」为机器可查状态（消费点清单进 ADR 附录，随 FEAT-068 普查产出）；过期未退役 → 升级为 BLOCKED 风险条目而非静默延期。
- **ADR-RB-4 per-unit lane 退化为「每 unit 一条小瀑布」。** 若 lane 序列（backlog→design→development→testing→…）在 unit 内部仍被实现/理解为全序推进，结构切换只是把一条 11-Gate 大瀑布切成 N 条小瀑布，用户语义（§2.9 正向条款）未兑现。缓解：lane 定义文档显式声明「lane 是状态分类，不是推进队列」——lane 变更由实际动作与认证驱动，无前置 lane 完成要求；行为验收场景 2（多 unit 并行）与场景 6（无 Gate 映射的高价值探索）作为反瀑布哨兵场景。

## 6. 实施路径映射（DEC-252 五步）

1. **本 ADR**（语义与权威先行——本票 FEAT-067）→ Design Reviewer R0 → 生效。
2. **FEAT-068：隔离副本本仓全链迁移**——dry-run → 人工核对 unit 划分 → apply → 成功认证 → 失败迭代 → 中断恢复 → 并发写入 → 回滚演练（N-3：回滚演练为验证门必过项）；checklist 复用 DEC-133 八项关闭标准；漂移校验（C-10 前置修复：证据绑定 §2.5 四元组）在本步落地；**不接受「运行时文件生成了」作为验收**。
3. **纵向切片贯通**：目标 → unit → 行动 → 验证 → 认证或迭代 → 事件落盘 → bootstrap 投影 → 新会话恢复；同步该切片的注入文本/热数据/验证器（不先改全部文案再等执行层）；五级主层级呈现须在既有投影预算（`_enforce_projection_budget`，bootstrap_aggregate.py L791-851）内达成，超出则走预算重定变更而非静默裁剪目标层（R0 修正 2026-09-26——D-5）。
4. **分族授权票切换**：按宿主/一致性边界分族翻转（复用 0.88/0.89 B-12/B-13 先例：机制先行+出厂 WARN+翻转留授权票）；新模型接线完整性先 WARN，安全/质量/授权底线不随 WARN 降级；每票执行 §2.4 权威署名切换 + §2.8 退役三要素登记；**授权票模板固定核查项 = 翻转 diff 含权威署名变更**（流程审查执行；机制化路径〔参照 task_status BLOCK 模式〕归属 FEAT-068 消费点普查产出——R0 修正 2026-09-26，D-6）。
   - **M7.4 step 6 调和（显式条目——R0 修正 2026-09-26，D-1；落地文件 `references/behavior-protocol.md`）**：§2.7 激励条款与现行 step 6b 选择域（「unblocked 任务 + 当前最高优先级」）及 step 6d（禁止结束会话）存在文本张力——当 unblocked 任务存在而目标贡献结论是「等待」时，6b 选择域容纳不了该输出、6d 又禁止结束。调和方案：① **step 6b 选择域扩展**——推荐候选域从「unblocked 任务枚举」扩展为「结构化推荐动作」，新增三类合法输出：「暂不新增动作（附目标贡献分析）」「终止低价值 unit（附论证）」「等待必要证据（附缺口与预计解除路径）」——输出仍为依赖分析驱动的结构化推荐，**不违反 step 6 的依赖分析必达/机录快照/用户确认机制**；② **step 6d 例外条款**——「推荐为正当等待/终止且该结论可追溯到目标贡献分析快照」时，会话可在无新增任务的情况下合规收尾（「无未完成任务或用户暂停」例外族增补）；③ 调和文本随该族授权翻转同批生效（翻转前 step 6 现文继续约束 classic 域行为——两套语义不跨域混用）；切片级最小调和（切片涉及的推荐输出）在步骤 3 同步落地。
5. **行为级验收与退役**：固定场景 × 多独立新会话对照。**七场景**：①紧急修复不重做前序；②多 unit 并行；③Gate 失败继续修而非宣告阶段失败；④目标变更取消任务；⑤证据不足暂不发布；⑥无 Gate 映射的高价值探索可入池被推荐；⑦运行时缺失或 unit 歧义时敏感动作等待确认而非静默降级。**验收禁令**：不以「出现 loop 词汇」或「next_gate 已删除」替代行为验收（DEC-252 裁决原文）。
