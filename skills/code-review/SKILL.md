# Code Review 规范

先明确本次变更要保障的用户行为和兼容约定。作者可沿用检查项自检，正式裁决交给独立 Reviewer。

## 循环角色

在内层 G6 沿真实调用方验证本轮改动，缺陷退还实现者。 独立 Reviewer 按[共享签核规则](../software-project-governance/references/loop-role-mapping.md)记录本轮回执与未解决阻断数。

## 输入与范围

审查工单、PR 或工作区指定的变更集。需要知道对照版本、期望行为和验收约束，适用的 ADR、项目规范及本轮运行回执按需读取。在已经接入治理的项目中，对齐计划中的成功标准。独立使用可直接依据用户指定的范围开展。

作者提交前自检适用的单元与集成测试、lint、类型检查及安全要求，交代变更原因、内容、验证方法和结果。Reviewer 按这些原件核对通过条件。

## 怎样验证一个发现

1. 通读变更。对每个疑点沿实际入口追到受影响的调用方或数据，核对变更前后的行为。即使出错位置在未改文件，也要定位到本次引入、暴露或加重问题的改动。
2. 核实触发条件。例如调用方是否已经校验输入、测试替身是否进入产品路径、疑似错误是否早在基线存在。优先查能推翻初判的契约、实现或测试。仍属猜测的事项写明缺少的事实和补验办法。
3. 对确认的问题写出变更位置、可达输入或操作、实际与期望行为、对用户或调用方的影响，以及可复验的依据和修复方向。对与变更无关的旧问题单列，风格意见按适用的项目约定处理。已知旧问题若违反本轮明示的发布或验收门槛，仍需报告门槛未满足。
4. 检查证据来自哪个版本、测试覆盖了哪个入口。已有失败日志或足以说明问题的调用链都可以引用。需要运行验证时，由拥有执行权限的人提供相应回执。

## 裁决依据

五个维度各给结论和依据。可合并引用同一份材料；某维度在此次变更中没有相关行为时说明原因。设计一致性需核对适用的 ADR 或既有接口契约。

| 维度 | 审查关注点 |
| --- | --- |
| 正确性 | 正常入口、失败或并发路径、旧数据和调用方的兼容 |
| 安全性 | 受影响的数据和权限边界、敏感信息、适用的安全要求 |
| 可维护性 | 变更是否重复现有能力，是否增加职责或偏离项目设计 |
| 性能 | 受影响路径的工作量、I/O 或资源使用，及对应预算 |
| 测试覆盖 | 测试能否区分错误和正确实现，项目对本次范围约定覆盖率时，复核其口径、阈值和此次实测 |

AI 代码专项的五项也各给结论：生产路径残留 mock、硬编码结果、调用不存在的 API、未实现的 TODO、超出任务范围的实现。关键词命中只是定位线索。比如测试夹具中的 mock 需沿引用路径核对其用途。

## 分级与输出

| 级别 | 处理 |
| --- | --- |
| P0 阻塞 | 必须修改，未解决 P0 数量须为零方可通过 |
| P1 关键 | 原则上本轮修复，允许遗留时须有明确处置计划和关闭期限 |
| P2 建议 | 给出可执行的改进建议 |
| P3 讨论 | 记录需要澄清的取舍或背景 |

报告先列已核实的发现，每项写明级别，再给各维度、专项及设计检查的结论。区分已满足、已证实违反、待验证的要求。可返工的阻塞问题或执行者在本轮范围可补的必需回执，返回 `NEEDS_CHANGE`，说明修复或补验方法。外部依赖、权限或架构决策导致本轮无法补验，或返工达到熔断条件时，返回 `BLOCKED`，写明依据和解除条件。门槛覆盖完整且通过，按是否有需保留的备注选择上文的通过终态。可选观察仍待验证时明确标注其范围，保留为备注。

作者逐条处理发现并提交修复证据。复审读取前轮报告、修复差异和同一验收标准，核对每个阻塞项及新引入的影响。独立审查报告可由 Coordinator 纳入 G6 的审查证据；独立使用时将报告直接返回请求方。
