## 1. 目标架构（组件图文字版 + 数据流）

### 1.1 分层组件图

```
┌─ L6 组合根：registry.py + CLI entry（唯一允许具名具体实现的层）
│      │ 按需 assemble()（不 import 单体即可选装一条命令）
├─ L5 引擎壳：verify_workflow.py —— 收缩目标：只剩 dispatch + gate 聚合（all_issues 汇总）
│      │
├─ L2~L4 领域模块（R2 执法：禁止 import verify_workflow；R3 执法：12 条白名单边、无环）
│   ├─ 存储域   state stores（.governance/*.json 规范源）+ append-only event log
│   │           唯一写路径 = CLI apply 函数；原子写 + CAS 版本
│   ├─ 状态机域 phase-legality 表 + 纯转移函数 + gate 求值（loop_paro_engine 模式泛化到任务生命周期）
│   ├─ 投影域   markdown 再生（release/projection 模式推广）+ drift check（Check 28b 模式扩面）
│   ├─ 迁移域   plan-hash 纯规划器 + dry-run/apply 恒等（loop_migration_plan 模式）
│   └─ 判断外壳域 verdict schema 校验 + 证据引用解析 + 后果派发表
│      ▲ schema 化 verdict（LLM→引擎唯一入口）   │ next-candidates / playbook（引擎→LLM 唯一出口）
├─ L1 数据资产：quickscan_registry / contract-matrix 快照 / core/*.json（只读事实源，registry 不复制事实）
└─ L0 contracts.py（形状定义，零依赖）

── 层外（持久侧，非软件层）──
LLM Coordinator 残留职责（封闭枚举）：
  ① 判断：triage / review / risk → 产出 schema 化 verdict JSON
  ② 交互：ask_user_question、升级处置
  ③ 开发本身：代码/文档变更（走 change-triage 入账门禁）
  ④ 异常处置：引擎 diagnostic 无法自分类时的人工裁决
 Coordinator 不再做：手写治理记录、闭环序列编排、状态解释（只读投影）
```

### 1.2 闭环数据流（record→evidence→tracker→锁→commit→push→后继）

1. Reviewer 产出 verdict JSON（结论枚举 + 证据引用 EVD/文件/检查 ID）
2. `review-record` ingest：schema 校验 → 判定面派发（NEEDS_CHANGE→round+1 / APPROVED→解锁）→ evidence 追加 → 状态翻转（原子写）→ 事件追加（state-first, event-second）
3. 序排器（引擎，非 LLM）求值 gate → 全绿则自动续步：tracker 翻转 → agent-locks 释放 → commit（模板 + task ID）→ push → task-priority → 产出 next-candidates
4. 任一步中断：状态库 CAS + 事件日志使 `close-loop --resume <task>` 幂等恢复——对"15 轮停滞需 interrupt"的软件级根治
5. 收尾：markdown 投影再生 + drift check 通过才允许 gate 通过

## 2. 五个裁决点

### 裁决 1 · 目标架构形态：**确认并完结既有六层架构**，任务生命周期状态机下沉到 L2~L4 确定性域

不发明新框架。把 0.80.0 六层从"雏形"定为正式目标；治理状态机（triaged→dev→review→approved→committed）按 loop_paro_engine 已验证三件套实现：phase-legality 合法转移表 + 纯转移函数 + 原子状态写 + 事件追加。LLM Coordinator 残留职责按封闭枚举，写入 SKILL.md 的不是描述性文字而是"Coordinator 输入输出契约"（进：投影摘要+diagnostic；出：verdict JSON+用户交互+代码）。

理由：机录路径零事故、手工 5 次事故全在确定性区——边界画在"判断 vs 确定性"是对的，缺的只是任务级生命周期纳入同款执法。六层 + ratchet 已让边界可执行（R2/R3 fatal），比任何文档化边界强。

反方案不取：「LLM 编排+强 prompt」（5 事故证伪 prompt 约束失效；每条护栏消耗注入预算边际递增）；「常驻服务/daemon」（插件市场分发模型不支持进程托管；CLI+git 文件即分发与审计通道；daemon=新增三类故障面）。

### 裁决 2 · markdown vs 结构化存储：**结构化单一事实源 + markdown 为再生投影**，推广 release-projection 先例为全局规则

存储/编辑/视图三分离——
- **存储**：每域一个 canonical JSON（.governance/*.json），只有 CLI apply 函数可写（唯一写路径）
- **编辑**：一律经 CLI 子命令（schema 校验 + 锁 + 事件追加）；LLM 手工编辑表格从"违规"升级为"技术上不可能写坏"（写错即 ingest 拒绝）
- **视图**：markdown 投影由引擎再生，头部标注"GENERATED — regenerate via …"；verify_workflow 扩 Check 28b（drift check）覆盖 plan-tracker/evidence-log/decision-log/risk-log——**投影漂移 = gate 失败**

反方案不取：「markdown 真相+强校验器」（LLM 既当解析器又当书写者不可救药——4 次表格事故实证；每条新校验=新 regex 解析器）；「SQLite」（牺牲 git 原生 diff/评审/归档，破坏 hooks/CI 依赖的"证据在仓库里"属性；JSON+原子写+事件日志同等事务且零新依赖——过度设计）。

### 裁决 3 · 闭环编排软件化抽象：**状态机引擎（幂等+可恢复）+ 事件日志作审计**——ADR-014 混合推广到任务闭环

状态库为运营真相；append-only JSONL 事件日志为可重放审计（state-first/event-second）；每步 = (task_id, step, 输入 hash) 确定性命令，重跑已完成步为 no-op。序排器先以"引擎打印 playbook、Coordinator 逐步执行"过渡，稳定后引擎直接执行。

依据：闭环跨越 git commit/push 与多存储，**不存在原子事务**——问题从"如何原子"退为"中断后如何确定性恢复"，即幂等状态机+审计日志的教科书场景，且已在 unit-loop 尺度验证（CAS 单调 + phase-legality 重放有测试）。

反方案不取：「mega-command」（伪原子——中途死=未知态无恢复记录，把停滞故障固化进软件；巨函数违反 R1/R4）；「完整 event-sourcing」（读者都要重放才知道状态，冲突 R6 启动预算；git 已是不朽历史，事件日志再当真相=双重记账。**事件溯源留作校验手段不作为读取路径**）。

### 裁决 4 · LLM 判断的质量外壳：**形式与后果软件化，实质留判断** + 三条防误软件化护栏

1. **Schema 化结论**：每类判断一个闭枚举 verdict 对象（review-record 已示范），扩展到 triage/risk 同构
2. **强制证据引用**：verdict 必须引用可解析锚（EVD id/文件路径/检查 ID），ingest 验证引用存在——无锚结论入口被拒
3. **判定面 = 可派生后果**：软件只执行"结论→后果"映射（NEEDS_CHANGE→next_round；APPROVED→解锁），永不软件化"结论内容本身"

三条护栏：
- **边界测试问句**（决策纪律）：「两个合格评审者对此输入是否可能合理地不同意？」是→判断区禁软件化；否→确定性区必须软件化
- **Ratchet 式审查钩子**：任何新增"解读判断内容"的代码必须在 decision-log 有显式条目（archguard 思路移植到判断边界）
- **逃逸阀遥测**：每条软件判定路径配 logged override（--reason）；定义不出 override=过度僵化；override 频率超阈值=边界画错位置（loop_telemetry 承载）

### 裁决 5 · 迁移路径：**渐进 strangler（已在进行）而非重写**——狗粮自举约束反而有利

R1（LOC 只降）+ R2（反向依赖只减）使迁移数学上单调；1MB 已验证单体（12 次审查拦缺陷的沉淀物）重写=丢弃全部已验证面。狗粮优势：迁移工具先在自己仓库演练（loop_migration 已示范），事故先伤己后伤用户——自举独有安全网。

## 3. 迁移路径草案

- **P0 冻结面**（已达成大半）：contract-matrix 快照 + ratchet R1~R7 fatal 化。里程碑：84 keys/71 segments 冻结、主文件停止增长 ✅
- **P1 存储分离**（先易后难，一表一版本）：risk-log 或 decision-log 起步 → 最后 plan-tracker（~430 行）/evidence-log（~1100 行）。每表=一次性 importer（plan_hash dry-run/apply 恒等 + 回环字节比对）+ 投影 + drift check 扩面。里程碑：①手写路径被 gate 阻断指向 CLI ②verify 全绿含新 drift check ③投影字节级再生
- **P2 闭环编排**：loop gate processor + event log 泛化到任务闭环（先幂等单命令，再序排器）。里程碑：**混沌测试**——commit 与 push 之间 kill 进程，`close-loop --resume` 零人工修复；进发布检查单
- **P3 单体收缩**：registry 点路径按命令族外迁（release/*、checks/* 已示范）。里程碑：verify_workflow.py ≤50%、冷启动进 R6 容忍表
- **P4 狗粮自举闭环**：插件自身发版走新管线。里程碑：一次完整发版（含一次 .governance 表迁移）全程**零 LLM 手写治理记录**
- **自举纪律**：双路径并存但权限不对称——手工路径不被删而是被 gate 指向（fail-closed 而非 fail-brick：引擎不可用时判断照常、只 BLOCKED 记录）；每阶段以正常版本交付

## 4. 蓝军挑战（含缓解）

- **BT-1**「CLI-only 写入让人变慢」→ 投影保可读 + CLI 引导式 + telemetry 量测编辑延迟劣化即回炉
- **BT-2**「引擎 bug=全部记录阻塞（新单点）」→ "degraded-but-honest" 形式化为产品状态（判断照常、记录 BLOCKED 响亮披露 + --emergency-append 带披露标记入隔离区待复审）；fatal 测试门+混沌测试兜底
- **BT-3**「迁移期双真相窗口」→ 单表切换压缩在一版本内；drift check 使双真相一会话内必现红灯；importer 恒等+回环比对
- **BT-4**「事件日志无界增长/重放成本」→ 日志是审计非真相按需校验；archive 轮转；R6 监控导入成本

## 5. 未问到但关键的 2 个问题（含初步答案）

- **Q-A 并发写入仲裁目标语义**：单一写者原则（引擎 apply 唯一写）消解大半；任务锁保留给"谁有权发起闭环"；存储行 cas_version（事件日志已有）使带外写入下次 verify 必然暴露并 BLOCKED——人改经 CLI 走同一锁，无第二写路径
- **Q-B 引擎失效时的用户体验（支持故事）**：把 "degraded-but-honest" 定为设计态而非事故：引擎拒判→LLM 明示"记录被阻塞，判断工作继续"；dsh_doctor/dsh_boundary 已是雏形，补《降级模式契约》进 SKILL.md + 升级确认门（FEAT-035 同款）告知用户

## 6. 复杂度上限声明（单人维护约束）

**六 patterns 封顶**：今后任何新机制必须是以下之一实例，否则视为过度设计拒绝——①registry 点路径选装 ②ratchet 只降不升 ③纯函数+fail-closed never-raise ④状态库+事件日志混合（ADR-014）⑤投影再生+drift check ⑥plan-hash 迁移恒等。零新运行时依赖（stdlib Python + git 文件）；无 daemon；无新存储引擎。每阶段 1~2 个插件版本；定义不出"单会话可验证里程碑"的阶段必须拆分。

**架构完工判据（一句话）**：LLM 手写治理记录数 = 0；引擎写全部状态；LLM 只产出 schema 化 verdict + 代码 + 散文。
