## 3. 越界清单（公理违例——重点）

> 每项含：事故实证 / 确定性论证 / 软件化候选形态。与 DEC-220 落地映射（FEAT-042/044/045 候选）对齐并扩展。

### B-1 plan-tracker 任务行状态翻转（手工行编辑）——P0

- **事故实证**：EVD-1101③（evidence-log.md L2351）——2026-09-19 会话 3 次行锚定失误（检测+修复）；DEC-220 记「3 次行锚定……全被 write-guard/复检捕获」。write-guard plan_tracker 脸（D11）只检 M1 签名（重复优先级列/行尾空单元格），**不能防「翻错行」**——锚定错误要靠人工复检发现。
- **确定性论证**：状态列取值封闭（⏳ 待执行/🔄 进行中/✅ 完成 + 日期 + 审查状态枚举），翻转规则完全由 M7.4 状态机（behavior-protocol.md L516-531）规定——是纯状态机操作，零判断。
- **频次**：每任务 2~4 次（派发→进行中→待审查→已完成 + 审查状态同步）。plan-tracker 现重 174KB——行锚定失败面随体量增长。
- **软件化候选**：`task-row-update` CLI——`--task --status --review-state [--date] [--note]`；按 task_id 唯一锚定（非行号），写前存在性 + 写后 M1 签名自检（Check 26 同族）；NEEDS_CHANGE 翻转拒绝（须走 review-record 链）。= **FEAT-042 候选的确认与细化**。

### B-2 decision-log 行追加/编辑（无写入 CLI）——P1

- **事故实证**：①DEC-220 记「1 次决策账入账截断」（2026-09-19）；②FIX-312——归档引擎误迁 DEC-187 出热文件（虽根因在归档判据 W-2，但暴露热文件行结构无写入器保护）。
- **确定性论证**：grep 实证 verify_workflow.py 53 处 decision-log 引用均为读取/校验/init 模板（L20407）；DEC 行的 ID 自增、日期、来源列、表格列形是纯机械操作。

### B-3 agent-locks 追加/修改（acquire CLI 不覆盖）——P2

### B-6 session-snapshot 手工全文——P2（混合面）

- **软件化候选**：`snapshot-render --write` CLI——从热数据投影骨架 + 引用 RECO/EVD 快照 ID（Check 34 契约内建），LLM 只填叙述参数。注意 legacy 通道：行为灰度回退「完整快照契约」时此 CLI 需保留 full 模式（FEAT-036 双契约）。

### B-7 快照/报告登记面（archive/index.md 等）手工维护——P3

- **事故实证**：FIX-343①——归档任务行回填 10 行 + index 同步全部手工执行（Coordinator 直写批）；AUDIT-125 期 index 与热文件漂移引发调查（archive/index.md 把 OPEN 风险列为已归档——FIX-169 恢复链）。

公理 ≠ 一切硬编码。以下实例证明「判断面被规则化」同样产生事故，边界必须双向检验：

## 6. 供 arch 顾问裁决的边界难题（Q-1~Q-5）

- **Q-1 状态机所有权与并发语义**：task-row-update CLI 化后，plan-tracker 行的**写者唯一性**如何定义？现状是 Coordinator 单写者 + agent-locks 防任务并发；CLI 引入后是否把「写者=CLI、LLM 只发指令」升级为硬边界？并行翻转同一行（两个任务同窗闭环）的冲突语义用 CAS（loop_paro_engine 先例）还是串行锁（M7.6a 现状）？
- **Q-2 closure-chain 的失败语义与协议双轨**：链中第 N 步失败（如 push 凭据阻塞、review 未机录、锁被占用）→ 断点续传还是整体回滚？事件载体是否复用 loop_event_log（append-only + restart-safe 已就绪）？过渡期 M7.4「agent 自觉协议」与 CLI 编排双轨并存时，以哪个为准（建议：CLI 可用 = MUST 走 CLI，不可用 = fail-closed 升级而非手写——review-record C8 先例）？
- **Q-3 evidence-append 的 schema 边界**：CLI 只管骨架（ID/日期/列形/非空），还是也机检 `事实依据:` 的**语义质量**（如引用文件必须存在）？后者会把判断面重新塞进规则（W-4 风险），前者留下「格式合规的空话」风险（Check 6b 既有问题）。裁决点：语义质量留给 Check 事后 WARN + Reviewer，还是 CLI 前置?
- **Q-4 门禁参数的数据化（provenance）**：85% 门事故（W-3）的根因是「规则消费的数字无新鲜度契约」。是否建立通用机制：任何数值门 MUST 携带基线来源 + 采集日期 + 失效条件（元数据 schema），过期门自动降级 ADVISORY 并触发重测，而非硬判 FAIL？这属于「给规则的数据面加确定性」，而非放松规则。
- **Q-5 机录自身的可靠性回归**：review-record 先例（FIX-314 键面碰撞、GBK 例外、FIX-284 写入行缺失路径）证明**CLI 也是会出 bug 的软件**——DEC-220 落地批量增大机录面后，是否将「写入器自身的写后自检 + 守护测试 + 灰度开关（behavior_profile 模式）」定为机录 CLI 的强制交付物清单（非可选项）？否则单点从「LLM 手滑」迁移为「CLI 回归」。
