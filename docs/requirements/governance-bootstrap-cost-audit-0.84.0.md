## 4. 测量口径校准（arch 顾问指出，防过度归因）

1. **1.6M 输入 token 是累计请求量，非上下文驻留量**——同一材料随 19 次请求反复计入；它证明"长上下文×多步骤"的放大，不证明单次塞入 1.6M。
2. **119K 上下文与分项不闭合**（2.7K+7.5K+67K≈77.2K，余 ~41.8K 未解释）——需埋点核实工具结果/隐藏消息/推理记录归属，不能全归因 27K 治理文档。
3. **计时分项可能重叠**（98 tok/s×18.4K≈188s 生成 + 19×3.5s≈66.5s 首token ≈ 254s ≈ LLM 4m14s）——后续埋点须按 TTFT/解码/工具执行/并行区间分离。
4. 五轮样本支撑中位数判断，不支撑稳定 p95；巨型会话累计时长含用户等待（ask_user_question 挂起 32m22s/9m11s/5m43s 实测）与闲置。

## 5. 根因链（arch 顾问判定 + 轨迹证实）

1. **决策权放错位置**：确定性工作（热数据读取/健康检查/候选过滤/迁移前置判定）以自然语言协议编码，由 LLM 概率执行——19 次串行往返，每次付 prefill+首 token；status 0.49s 的确定性能力已存在但协议仍要求 LLM 读 plan-tracker 热数据 6 段。
2. **观察-裁决-迁移-展示串成阻塞事务**：用户未表达目标前先付全量治理税；Scenario C 升级路径在交互前执行写操作（读入口与写迁移耦合）。
3. **注入面重复且无预算**：AGENTS.md/CLAUDE.md 双份 bootstrap 模板（本仓库两者都注入）；660 行命令文档全文加载（含当前无关 Scenario）；plan-tracker 巨行直读（行数限制在数千字符单行前失效）；Delivery Trust Snapshot 24 字段强制输出。输出量 ×98 tok/s 直接乘出用户等待。
4. **自增负担回路**：治理数据膨胀（evidence-log 1.5MB）→检查变慢（31s→50s）→检查/审查再产生治理记录；子代理派发复制完整治理主体（角色定义全文+skill+上下文，55~60 步/62~85 工具调用常见）而非有边界任务信封。

## 6. 架构边界判定（arch 顾问）

> "用更明确的文字要求模型少读、少调用，不能替代执行层预算和确定性编排。"

| 工作 | 推荐执行方 |
|---|---|
| root 解析、版本兼容、权限判定、热数据读取、状态汇总、检查选择、缓存有效性、门禁裁决、面板字段采集、候选过滤 | **确定性工具** |
| 用户目标澄清、优先级冲突、方案取舍、模糊风险判断、复杂代码审查、执行计划建议 | **LLM**（由工具校验权限和前置条件） |

治理税定价原则：**固定底税极低，风险操作按需加税，后台维护按变化和预算计费。**

建议预算（产品 SLO，非行业定律）：静态注入 ≤4K tok 且 ≤3%W；首次交互前治理新增驻留 ≤10K tok 且 ≤5%W；bootstrap 模型生成 ≤1.5K tok；首次有效交互 p50≤15s；普通会话治理主动耗时 ≤10%（超 20% 触发架构复审）。

这是**治理控制面侵入用户交互关键路径**的问题，不是 Python 启动慢，也不只是文档太长。

目前系统把"每次进入治理"实现成了"让 LLM 重新解释治理协议、收集状态、执行检查、处理迁移、组织完整报告"。结果是：

1. **已有确定性能力没有成为执行入口**：`status` 已经 0.5 秒，但协议仍让 LLM 读热文件；quick-scan 已交付，但实际路径仍跑全量检查。
2. **观察、裁决、迁移、展示被串成一个阻塞事务**：用户尚未表达本次目标，就支付了完整治理成本。
3. **优化停留在输出层，未改变执行复杂度**：`summary-only` 缩短结果，不缩短检查；缓存输入降低计费，不降低输出生成量及串行交互次数。
4. **缺少治理自身的资源预算与退出条件**：系统有质量门禁，却没有"交互前最多允许多少步骤、token、耗时"的门禁。

**推荐方向：确定性、只读、预算受控的 bootstrap 控制面 + 风险分级门禁 + LLM 按需决策。** 默认使用 lite profile，但保留安全底线和高风险操作的强制检查。不要把 lite 等同于关闭治理。

### 诊断要点

**诉点 1（五分钟才交互）**：两个独立瓶颈。A. 模型编排瓶颈——约 74% 墙钟在 LLM 侧，仅优化检查器（工具归零）仍有 ~4min 模型时间，必须同时减串行往返/输出 token/模型自行解释的材料。B. 检查器瓶颈——`--summary-only` 是"全量计算+摘要渲染"而非"快速摘要查询"，可修缺陷。版本升级路径在交互前读变更日志、算 diff、改文件是读入口与写迁移耦合——即使迁移必要，也应先显示"升级待处理"。

**诉点 2（上下文消耗）**：工作集选择错误——当前场景只需一个分支却携带完整流程手册；状态查询只需结构化字段却读 Markdown 原始表格；工具已给事实仍要模型从文档推导；治理中间产物常驻会话。读"前 120 行"不是有效预算（单行数千字符时行数限制失效）。27K 只是显式材料，还须治理工具结果膨胀和执行过程膨胀。

**诉点 3（治理自耗）**：always-on + 固定完整启动 + 每次完整面板 + 子代理重复 bootstrap + 治理记录增长致检查变慢——潜在自增负担回路（需 profiling 证实超线性，但"无有效上界"已可确认）。子代理 55-60 步提示角色分离被实现成"复制完整治理主体"而非"派发有边界的任务"——审查分离的价值来自独立判断和证据约束，不来自每个角色重复加载全部管理历史。

### 窄腰接口建议

```
平台薄适配器
    ↓
bootstrap 查询 API / CLI
    ├─ entry resolver / status projection / quick-scan orchestrator
    ├─ evidence freshness / cache / candidate filter
    ↓
有界结构化结果（≤2K token 投影）
    ↓
LLM 澄清目标、解释取舍
    ↓
写操作 / 交付操作的独立门禁
```

六层架构和分层绞杀可继续推进，但层次清晰并不自动减少一次 LLM 往返——本次优先修执行关键路径，避免先花一个版本搬 24K 行代码却不改变体验。

### 按 ROI 排序的方案

**P0 交互前置+移除启动写迁移**：用 resolve_entry+status 提供状态/阻塞/≤3 候选；获得目标前不读全部 Scenario、不生成完整 Snapshot、不自动编辑治理文件；健康检查未完成标"待检查"非绿色通过。首次有效交互分钟级→10-25s 量级。风险：只是"先 ask 选完再等三分钟"是虚假改善——必须同时跟踪进入实质工作时间。**立即做。**

**P0 输出预算+注入去重**：24 字段拆两份契约（完整机器 artifact + 默认交互视图：目标/进度/阻塞/健康覆盖时效/下一步/需用户决定项；权限风险、已知 FAIL、证据缺失不得因折叠隐藏）。bootstrap 模型生成预算 ≤1.5K tok（超预算需显式原因码），用户可见摘要 300-700 tok。18.4K→1.5K 同速率省 ~172s——比优化 Python 启动重要两个数量级。注入：AGENTS/CLAUDE 单一规范生成薄适配；skill 只留路由/预算/关键约束；command 入口只留分派信息；禁止默认读完整 plan-tracker。预算表：静态常驻 ≤4K / bootstrap 工具返回 ≤2K / 模型生成 ≤1.5K / 动态余量 ≤2.5K。CI 用实际 tokenizer 检查实际加载集合。

**P0/P1 单命令聚合 bootstrap**：`governance bootstrap --profile lite --format json --budget-ms 3000`——默认只读幂等；单次读取共享解析；超预算返回部分结果+未完成范围（不猜测通过）；不执行迁移不启动子代理。验收：数据收集 1 次 CLI、首次交互前总工具 ≤3 次、串行模型决策节点 19→2-4。仅 TTFT 节约 ~50-60s。风险：聚合 CLI 成为另一个巨型函数——复用现有 resolver/status/quick-scan 作编排层而非复制逻辑。

**P1 quick-scan 接为交互 summary 默认**：先审计调用方，加 `--scope quick|full` 契约（发布流程显式固定 full）。46-50s→目标 1-3s。四态契约必须带覆盖范围/来源快照/检查器版本/证据时间/待检查项/门禁效力——"快速范围通过"≠"完整治理通过"。shadow 不应变成每次启动后台全量重跑：灰度扩大采样→稳定后按风险/数据变化/抽样触发；同快照 single-flight；过期结果不得覆盖当前状态。

**P1/P2 治理数据生命周期**：先 profiling（按解析阶段/检查段/检查项记录时间与扫描字节数——1.5MB 扫 50s 可能是多检查重复解析/嵌套循环，需证实非直接认定）；单次运行共享解析模型和索引；分离活跃状态与不可变历史证据；归档触发到执行闭环追踪；超阈值热文件阻止无约束追加。目标：热 evidence 回 200KB 内；历史增长 10 倍 bootstrap p95 增长 ≤20%；巨行不进默认上下文。先复用现有归档+索引，profiling 证明值得再考虑 SQLite，不建议现在上数据库。

**P2 子代理任务信封**：只传任务目标/验收/权限范围/相关文件/证据引用/简短角色约束/输出格式与预算；默认禁止递归 bootstrap。验收：固定角色材料减 ≥70% + 审查漏检不增加。

### 治理税判断

价值成立（跨会话协作/发布/安全/大规模重构/审计追溯），但当前收费方式不成立（查询状态/解释代码/小修文档/探索讨论中完整 bootstrap 可能比任务本身贵）。trigger_mode 解决触发与展示，不解决检查深度——silent 仍可能很贵。Profile 分层：lite（默认：status+quick-scan+简短交互）/ standard（受影响检查+变更证据+风险驱动审查）/ strict（发布/安全/权限/迁移：完整门禁+独立审查）。权限边界和不可逆操作确认不因 lite 放松。

### 盲点清单

1. 展示状态不应拥有修改项目的隐含授权（bootstrap 默认只读也缩小提示注入影响面）
2. 治理文件应作为数据而非可执行指令（结构化投影同时改善性能和安全）
3. 异步健康结果需要快照一致性（旧快照 PASS 不能成为新变更的发布凭据）
4. 不能用"后台化"掩盖总成本（后台 scan/子代理/自动审查都进治理账单+并发上限+去重）
5. 不能只优化首次 ask（须观测选完之后多久真正开始工作）
6. 瘦身不牺牲质量的证据需单独建设（故障注入和缺陷基准，证明没把 fail-closed 偷换成未验证 pass）

最终应把 /governance 从"执行一遍治理仪式"改造成"读取一个可信、轻量、可行动的治理快照"。完整检查、证据闭环和独立审查仍然存在，但只在其结果会影响下一步决策时进入关键路径。
