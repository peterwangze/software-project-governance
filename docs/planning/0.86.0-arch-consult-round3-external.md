## 总裁决

**维持 NEEDS_CHANGE，三个 P1 都应在设计层关闭后才启动批 1 并行实施。**不需要推翻既有路线，也不需要增加运行时依赖。边界：0.86.0 范围仍 M0→M3；单人维护下"并行"主要指任务可独立推进，不值得为抢跑引入隐式依赖；预授权执行与发布仍有效，但"设计打磨完成"不能由实施完成倒推；验收和回退规则必须同时进入设计文档与版本规划（防双源漂移）。

| 问题 | 推荐裁决 |
|---|---|
| P1-1 | **M0 独立成票，设批 0，作为批 1 的显式阻塞依赖** |
| P1-2 | **先补最小可信基线；历史相对改善指标暂记 NOT_EVALUABLE，不阻塞可独立验证的功能目标** |
| P1-3 | **改为"完整交付/明确延期/撤回规划"三选一；降级姿态作为运行策略单独建模，不冒充交付完成** |

## P1-1：M0 独立承载票（批 0）

交付物：contracts.py 或等价单一契约位置/版本化契约 fixtures/可运行契约测试/三张批 1 票的契约引用与变更规则。至少冻结：operation_id 产生/作用域/重试复用/同 ID 异载荷处置；状态与合法迁移（**执行态 UNKNOWN 与评估态 NOT_EVALUABLE 的区别**）；错误码及重试/人工分类；schema 版本字段/兼容规则/未知版本处理；写入器最小输入输出与效果判定契约。**M0 冻结跨票接口非全部内部细节。**

依赖图：批 0（契约+fixtures）→ 契约测试通过冻结 revision → 批 1（各票用同一冻结 revision）→ 批 2.0（复跑 M0 契约测试+跨票集成验收=**兼容性回归非补做验收**）→ closure/混沌发布门。批 1 发现契约必须变更→提出变更→更新 M0 基线→识别受影响票→重跑相关验收——不能由实现票直接改共享语义再让其他票追认。

反方案：并入批 1 某票首交付物不推荐（除非拆成显式前置子票其他票等待验收=实际上就是批 0；否则"整票未完成但接口已被消费"隐式依赖）；降级为共享 DoD 拒绝（DoD 可要求"符合契约"但不能替代"谁生产/何时冻结/谁验收"——把生产依赖伪装成检查清单）。

关闭证据四项：M0 谁交付/产物在哪/验收命令/哪些票被阻塞——齐全才关闭。

## P1-2：拆开"历史改善证明"与"新版本绝对目标"

不等待 M2 才量测，不继续引用无出处的"0.85.0 ≥5 段"。修法：删除或标注撤回该事实性表述；"4 段/5-8 步/≥5 段"列**待核实历史陈述**不得合并为一个数字；建立最小基线采集任务（优化验收前完成）；验收拆三维——历史相对改善（无可信基线=NOT_EVALUABLE 不能宣传达成）/新版绝对目标（规定路径 ≤2 可独立测量但须先明确适用路径定义）/机制正确性（原子/幂等/恢复/门禁按功能与故障测试验收，不受旧基线缺失影响）。**冷启动不是不量化，而是先冻结量测协议再采样再下结论。**

量测协议要素：LLM 往返定义（一次逻辑模型请求响应计一次；流式分片不另计；工具结果后再响应另计；传输层重试单列）；测量起止点；标准/异常路径分类；是否含规划评审返工；人工干预/提前退出/失败样本记录；模型/提示模板/工具配置/代码 revision/测试用例；原始 trace 保留。固定用例组（标准成功/冲突/恢复）旧新同协议测量。目标只是"标准 closure 路径 ≤2"就明确如此，不写"每票 ≤2"（后者含设计复杂度与人工评审，非写入器可控变量）。

记录位置：`benchmarks/closure/{protocol.md, cases/, runs/<run-id>/{manifest.json, results.jsonl, summary.md}}`——标准库生成，记时间/revision/配置/结果/trace 引用；敏感脱敏；**测量工件 JSON ≠ 业务存储 JSON 化前移**。M2 后作为证据引用导入（保留原始测量时间+导入时间，不伪装 M2 自动生成）。

目标数字处理：有 trace 统一协议重计；无 trace 但旧版可运行=旧版重演基线（明确非"历史实测"）；无法恢复等价环境=相对指标 NOT_EVALUABLE 记原因+绝对目标照常测。**不得测得新版 3 次后为过门改门槛 3**——改目标=有理由有版本记录的需求变更。

反方案：等 M2 才建基线不推荐（新版写入器不能自动创造旧版 provenance；易失可比条件）；强制恢复历史数据否则停工不推荐（历史不可评估但功能正确性可独立证明）；仅"履行量测义务"不足（解决证据缺失但不替代新版可量化路径目标）。

## P1-3：交付裁决与运行处置分开

原 A/B/C 未闭合：A 同时涉及延期与部分发布；B 是运行姿态也意味着能力未完成；C 是规划状态；A/B 可同时发生非互斥。**BLOCKED+响亮披露≠满足 DoD**——只能诚实表达未完成。

第一层交付裁决三选一：A 完整交付（修复过原 DoD，必要时顺延整个发布——本版目标完整完成）/B 明确延期（本次不交付该面，承诺迁入确定后续里程碑——范围调整不得宣称原范围完成）/C 撤回规划（撤销实施承诺回 planning 重判必要性与方案——无确定交付承诺）。B/C 区别=是否保留确定交付承诺。R1 改写为：「DoD 不得静默降低。原范围未完成时只能整体顺延或通过显式范围变更批准延期/撤回；部分发布不得标记原计划完整完成。」若坚持范围绝不缩减则 B/C 只用于后续规划、当前版只能选 A——**此逻辑取舍必须明写不能靠措辞兼容**。

第二层运行处置（可组合）：禁用/只读/用已验证旧路径/启用预先定义并单独验收的降级 profile/无法安全隔离则阻止发布。behavior_profile 不是豁免标签——必须提前规定可用禁止操作/必须满足的安全一致性不变量/明确失败方式/进入退出条件/恢复测试。降级 profile 若本就是已批准交付目标可按自己的 DoD 验收；**不能故障后临时发明 profile 把原目标改称已完成**。状态分离：实现状态（BLOCKED/...）/交付裁决（deferred/withdrawn/...）/运行姿态（disabled/read_only/validated_fallback/...）——不塞进一个"完成态"。

"其余照发"硬边界：必须证明该面可隔离且其余能力不依赖其未满足契约；M0/核心写入器/effect-based resume 基础不变量不能因"其他票已完成"被绕过发布。撤销功能≠撤销历史副作用——已发生文件/提交/外部动作按前向恢复与 git 边界收尾。

反方案：保留"降级采纳"加强披露=拒绝（披露不能恢复正确性）；所有故障一律撤回 planning=不推荐（丢修复承诺与确定性）；依赖回滚=拒绝（违前向恢复与不可逆副作用原则）。

## P2 四项意见

**a) BT-8 绕行搭便车**：「接口契约非权限隔离」判断正确，但机器来源标记 join 只能一致性检查不能证明来源真实。分层检测：冻结受管文件/字段与允许写入器清单→写入器记录 operation_id/受影响对象/前后内容摘要/对应证据→release/CI 检查实际变更与操作记录效果匹配→检查缺失记录/孤儿记录/摘要不符/同 ID 异载荷/非法迁移→故障恢复先处理未完成操作再判绕行（防合法崩溃窗口误报）→hook 本地提醒+正式发布检查必经。**边界声明：能发现未记录修改与普通绕行，不能抵抗同权限下能同时伪造文件/记录/校验流程的攻击者——真防恶意写者需仓库权限或受保护 CI，不承诺零依赖库内代码实现。**至少覆盖"无记录直接修改/伪造标记内容不匹配/合法崩溃中间状态"。

**b) BT-9 Windows/CI kill 注入**：子进程写入器+父进程测试控制器+命名故障点——不用 TTY 不依赖 SIGKILL 常量。子进程到指定故障点发握手消息暂停→父进程标准库 subprocess 终止→等退出→新进程恢复→检查状态/效果/重复执行。Popen.kill() 在 Windows 用相应终止机制；写入逻辑尽量单子进程避免跨平台进程树清理。故障点放协议边界（临时文件写入后/同步后/替换前后/效果完成但记账前）。**区分硬终止（清理逻辑无机会执行的崩溃）与抛异常（正常错误处理）两类测试；进程 kill≠掉电/存储故障——报告不得推导为断电持久性保证。测试注入接口仅存内部测试入口不向生产 CLI 暴露。**

**c) FEAT-046 文件面冻结时点**：初步 triage 收集→文件归属/写集分析→冻结"新增还是并入"及文件面→最终 triage/批次分配→批 1 启动——**最终宣告票可并行之前冻结，而非实施后补**。M0 产物为共享只读依赖（修改触发契约变更流程）。共享文件采用**指定 owner+串行集成**通常比"不同段落所以不相交"更稳；文件面仍重叠就修改批次依赖，不为形式并行拆碎文件。

**d) "零手写"量测定义**：更名「**受管状态变更零人工直写，且全部变更可与合法写入操作对账**」。排除正常业务判断/文档说明输入——人可提交命令参数但不能直接编辑受管状态。三指标分开：未对账变更数=0（受管文件变更是否都有合法操作解释）/对账覆盖率=100%（列明覆盖文件字段范围）/人工恢复干预次数（标准路径要求零，故障路径单列不隐藏）。手工路径计数器与 hook 拦截次数仅辅助指标（绕过 hook 不被计数）；真正验收比较**验收窗口起止快照、差异与操作记录**。证明的是"验收范围内没有未记录直写"非"维护者从未打开编辑器"。无需 telemetry 服务。
