# 企业实践参考

当前单元出现具体缺口时，负责人可以借用以下实践。把所得观察交给该单元的执行人或独立评审人，继续按原目标和验收条件裁决。

| 当前需要解决的问题 | 可采用的做法与产出 | 资料来源 |
|---|---|---|
| 团队对用户最终能得到什么有不同理解 | 用 Working Backwards 的 PR/FAQ 描述成品与使用场景，让需求方核对。需要衡量效果时，用 OKR 明确可观察结果。 | Colin Bryar、Bill Carr，《Working Backwards》；项目调研的 Google 与字节跳动 OKR 条目 |
| 设计取舍影响多个模块 | 通过 Design Doc 或叙述文档写清选择、替代方案和后果。请独立角色针对主要假设提出反例。 | 《Software Engineering at Google》；项目调研的 Amazon 叙述文档和华为蓝军条目 |
| 代码变更或运行结果需要独立判断 | 将变更和可复测观察交给 Code Review。遇到用户行为不确定时，可用试用或对照实验获取证据。 | [Google Engineering Practices](https://google.github.io/eng-practices/)；项目调研的字节跳动实验实践 |
| 出现质量事故或结果低于预期 | 用无责复盘梳理事件与原因，让负责单元执行修正并再验证。需要跨职能判断时，可参考 IPD 的联合评审。 | 《Software Engineering at Google》；项目调研的华为 IPD 与自我批判条目 |

项目调研按公司列出了原始来源和案例，并区分书籍、官方文档与公开报道。详见 [企业实践调研原件](https://github.com/peterwangze/software-project-governance/blob/7b9fd3720376549c53b06d4fc362f5fb0c96e40b/project/workflows/software-project-governance/research/company-practices.md)。
